## 0. 结论速览

| 你的问题 | 答案 | 确定性 |
| --- | --- | --- |
| HID 能读到什么 | 实时测量（V/I/D±/CC1/CC2/温度）、设备身份（SN/固件版本/厂商/UID）、PD·UFCS 报文原文、少量事件文本 | ✅ 已实测 157k 帧证实 |
| 能读到离线记录吗 | **不能**。命令集已完整枚举，没有任何"读记录文件"命令；设备→主机每帧固定 64 B、一问一答，没有流式传输 | ✅ 固件命令表 + 抓包双重证实 |
| 能读到开机图吗 | **不能**。固件只在本地 `f_open("0:logo/logo.bmp")` 读进屏幕，那条路径没有任何 HID 出口 | ✅ 固件代码级证实 |

**一句话**：HID 通道是**遥测 + 控制**通道，不是**文件**通道。凡是存在 4 MB Flash FAT 分区里的东西
（离线记录、开机图、主题、字库），HID 一律碰不到，只能进 U 盘模式（按住「返回」键插线）取。

## 1. 重大修正：主机→设备有 **三类帧**，不是只有 `AA`

此前认知是"HID 命令只有 INFO / START / KEEPALIVE 三条"，**不准确**。
命令解析函数入口在 **0x0804A704**，它是唯一的 HID 出口接收处理：

```
0x0804A71A  ldrb  r6, [r1, #1]        ← buf[1] = LEN
0x0804A728  bl    #0x802bc70          ← CRC16 计算（poly 0x2507 / init 0x11 / +1）
0x0804A72E  cmp   r1, #0xaa           ← buf[0] == 0xAA ?
0x0804A730  bne.w #0x804a88e          ← 不是 → 转 0x55 / 0xA5 分支
0x0804A736  ldrh  r2, [r2, #-0x2]     ← 取帧尾 CRC
0x0804A740  cmp   r2, r0              ← CRC 不符 → 直接丢弃（设备完全不回）
0x0804A754  cmp   r0, #6              ← CMD > 6 → 走 START 分支
0x0804A75A  tbh   [pc, r0, lsl #1]    ★ 命令跳转表，表基 0x0804A75E，7 项（CMD 0..6）
```

`buf[0] != 0xAA` 时会落到 **0x0804A88E**，那里还有两路：

```
0x0804A88E  cmp  r1, #0xa5  → 0x0804A8EE   ← A5 帧
0x0804A892  cmp  r1, #0x55  → 0x0804A898   ← 55 帧（否则丢弃）
```

### 1.1 `AA` 命令帧（控制类）

| CMD | 处理入口 | 功能 | 官方上位机在用？ |
| --- | --- | --- | --- |
| 0x00 | 0x0804A76C | **INFO** —— 回 0x1A 信息帧（SN / 固件版本 / 厂商 / UID / START 挑战参数） | ✅ 用 |
| 0x01 | 0x0804AC3E | 置 `strb 0,[sb,#3]` → **暂停数据流** | ❌ 未见使用 |
| 0x02 | 0x0804A9A6 | 回 0x0B 文本事件帧，内容为 `"accept"`（实测拼字节 `63 61 63 65 70 74`） | ❌ |
| 0x03 | 0x0804AAAA | **协议监听开关**：`buf[3]`=1开/0关，`buf[4]`=类型（0=PD / 1=UFCS） | ✅ 用 |
| 0x04 | 0x0804AACE | 💀 **破坏性，禁止再发**：`FLASH_Unlock` + **`FLASH_EraseSector(0x08007800)`** + 只写回 5 个字 → 削掉固件 2 KB → 设备被打进 IAP（2026-10-12 实测事故，见 §7.1） | ❌ 官方从不用 |
| 0x05 | 0x0804AC2E | `strb 0,[sb,#2]` + `strh 0,[sb,#0xA]` → **彻底关流** | ❌ |
| 0x06 | 0x0804AC4A | `strb 0,[sb,#4]`（清超时计数）→ **KEEPALIVE 续期** | ✅ 用 |
| >6（0xFF） | 0x0804A920 | **START**：校验 `buf[3]=='r'`(0x72) 且 `buf[8..9]` 参数 == 设备内部 `[sb+0xC]` | ✅ 用 |

> START 的"挑战-应答"在这里**坐实**了：`0x0804A92E ldrh r0,[r5,#8] → cmp r0, [sb+0xC] → bne exit`。
> 参数不对，设备一声不吭。这正是 INFO 帧里那两个字节（`33 32` / `dd 80`…）的用途。

### 1.2 `55` 帧（**主机→设备灌数据**，静态推断，抓包中 0 次出现）

```
0x0804A8AA  cmp  r1, #0x18            ← LEN == 24 ?
0x0804A8B0  bne  #0x804a96a           ← 不等 → 分包路径
    LEN==24：memcpy(0x20005C08, buf+2, 48)，回帧类型 0x22
    LEN!=24：0x0804A97E  ldrb r0,[r5,#1]
             0x0804A984  rsb  r0, r0, r0 lsl #5     ← r0 = LEN*31
             0x0804A98C  add.w r0, r1, r0 lsl #1    ← dst = 0x20005638 + LEN*62
             0x0804A992  movs r2, #0x3e             ← 62 B
             0x0804A994  bl   memcpy                ← 按 LEN 索引分包写入 RAM 缓冲
```
- 缓冲区基址 **0x20005638**，单包 62 B，索引上限 255×62 ≈ **15.9 KB**
- LEN=24 时落点 0x20005C08 = 0x20005638 + 24×62，**两条路径指向同一缓冲区**，自洽
- 方向是**写**（主机→设备），对应固件里的 `"HID IAP"`（@0x0800705C）与 `0:main/iap.bmp`（@0x0800704C）
- **抓包里一次都没出现过** → 官方上位机不用，属于产线/升级保留通道

### 1.3 `A5` 帧（配置类，需 `buf[0]==0xA5` 且 `buf[1]==0xA5`）

| 子命令 buf[2] | 入口 | 功能 |
| --- | --- | --- |
| 1 | 0x0804A908 | 停止数据流（`[sb#7]=1, [sb#8]=0, [sb#3]=0`） |
| 2 | 0x0804AD84 | **下发配置/校准表**：把 `buf[0x18..0x27]` 4 个 u32 写入 `0x20005398 + idx*0xC + 0x100..0x12C`，并 memcpy 到 `0x200070FC + idx*0x14` |
| 3 | 0x0804AFA0 | 直接回 64 B 响应 |

### 1.4 设备→主机：**永远是一问一答的 64 字节**

所有命令分支最终都汇到同一个出口：

```
0x0804AF2A  add.w  r1, sb, #0xe       ← 响应帧缓冲
0x0804AF2E  mov    r0, r4             ← HID 句柄
0x0804AF30  movs   r2, #0x40          ← 64 字节，常量
0x0804AF32  bl     #0x8049a88         ← 发送
```

**没有第二个发送出口能带长度参数**，也就是说不存在"分包回传"。
单包 62 B、167 Hz 满速理论也就 ~10 KB/s，且固件根本没实现分块上传 —— 离线记录（几十 KB 起）无路可走。

## 2. 能读到什么（设备→主机实测，157,137 帧）

对 `baseline_sniff / pd_capture* / pd_corr / pd_event_test / open_cmd*` 共 12 个日志统计同步头 `0x55` 后的类型字节：

| 类型 | 帧数 | 内容 |
| --- | --- | --- |
| `0x1B` | 157,001 | **测量帧**：VBUS(f32@+3)、IBUS(f32@+7)、D+/D-/CC1/CC2(u16 mV)、温度(u16 ℃)、序号(0..9) |
| `0x1A` | 61 | **信息帧**：SN（X3=BCD / SE=HEX）、固件版本（0xC8=V2.00）、厂商、UID、START 挑战参数 |
| `0x30` | 8 | **PD/UFCS 报文原文**（长度码 0x0C/0x10/0x20/0x28… = 数据长度+5），可解 Msg 头/PDO/RDO |
| `0x0B` | 13 | **文本事件帧**：`accept` 等事件标签 |

**157k 帧里除了这 4 类，一个别的类型都没有。** 没有文件帧、没有块传输帧、没有记录回放帧。

另外**读不到**的（必须由上位机自己算）：
- 容量 mAh / 能量 Wh —— 是 PC 端对电流/功率的积分，设备只给瞬时值
- 设备设置项（OL-Start / OLSI / RTSI / 亮度…）—— 只能经 `A5` sub2 **写**，没有对应的读命令

## 3. 离线记录：读不到（四重证据）

1. **命令表已完整枚举**：`AA` 帧 CMD 只有 0..6 + 0xFF，`A5` 帧只有 sub 1/2/3，`55` 帧只有两种长度分支。**没有一条是"读记录/列目录/读文件"**。
2. **通道结构上不可能**：设备→主机固定 64 B 单帧出口（0x0804AF32），无分块、无序号、无长度协商。
3. **记录的写入方向是 FatFs → 本地盘，不是 HID**：
   - 保存函数 0x0800DA46 起：`sprintf` 拼 `data/%02d_%dSec.bin`(@0x0800DAD4) 或 `%dms.bin`(@0x0800DAE8)
     （记录时长 ≤99 s 用 Sec 模板，>99 用 ms 模板，`0x0800DA54 cmp r1,#0x63` 判的）
   - `f_open`(@0x0802D8D0) 以 `0x32`(新建+写) 打开，然后 `f_write`
   - 打包循环在 0x0800D980-0x0800DA46：`strb/strh` 逐字段塞进缓冲，**每样本 8 字节**（`add.w r4,r4,#8`）
4. **读记录的代码只服务本地 UI**：全镜像 `f_read`(@0x0802DD00) 只有 9 个调用点
   （0x08006FEE / 0x08012A92 / 0x080180E8 / 0x08027C5C / 0x08027D40 / 0x0802E744 /
   **0x0803008A=开机图** / 0x0803BFA6 / 0x0803C182），
   **没有一个是 HID 命令处理函数**（HID 解析在 0x0804A704，跟这些地址八竿子打不着）。

### 顺带：离线记录 .bin 的格式可以从固件反推

打包循环（0x0800D980 起）显示每样本 8 B，且有一条 4 B/样本的第二通道
（`0x0800D9CE` 起：两个 u16 拆成 4 个 `strb` 大端写入）。字段来源数组与缩放系数还需再挖一轮，
但**有真样本就能一次定死** —— 取样本必须进 U 盘模式。

## 4. 开机图：读不到（代码级证据）

开机图读取函数 **0x08030008**（报告 §4 那条），完整流程：

```
0x0803000C  movw r0,#0x5dc4 / movt r0,#0x2000   ← 0x20005DC4 文件对象
0x08030014  adr  r1,#0xd0                        → 0x080300E8 = "0:logo/logo.bmp"
0x08030016  movs r2,#1                           ← FA_READ
0x0803001A  bl   #0x802d8d0                      ← f_open
0x0803001E  cbz  r0, #0x8030070                  ← 成功
0x0803005C  adr  r1,#0x98                        → 0x080300F8 = "Logo File Open Fail"（失败分支）
...
0x08030088  movs r2,#0x36                        ← 54 字节
0x0803008A  bl   #0x802dd00                      ← f_read 读 BMP 头
0x08030098  mov.w r2,#0x1e0                      ← 480 = 240×2
0x0803009C  strd r0,r2,[r1,#0x20]                ← 存宽高 → 直接上屏
```

**整条链路只有 FatFs + 屏幕驱动，没有任何 HID/USB 发送调用。** 读进来直接画到 240×240 屏上，
不会也不能往外吐。

## 5. 那到底怎么才能拿到这两样

| 目标 | 路径 | 状态 |
| --- | --- | --- |
| 开机图 | 按住「返回」键插线 → U 盘模式 → `logo/logo.bmp`（240×240 RGB565，BITMAPV4HEADER 56 B） | **可直接做**。手机上 OTG 读 FAT 卷，读/替换都行 → 手机端可以加"自定义开机图" |
| 离线记录 | 同上 → `data/NN_<时长>Sec.bin` / `NN_<时长>ms.bin` | 文件能拿到，**格式未逆**（见 §3 末尾，需样本） |
| 都不想按键 | 唯一软件路径是让厂商在正常 HID 模式加一条"重启进 IAP/U 盘"命令 | 固件里 IAP 模式代码齐备，加一条命令即可；现在没有 |

- Android OTG 挂 U 盘 → `UsbManager` + `libaums`（纯 Java FAT 实现）或 Storage Access Framework
- 注意是**双 LUN**（RKX3 + RKX3IAP），两个卷
- 已确认的事：设备 U 盘文件体系见 `固件V2.00-解析报告.md §1`

## 7. 实测记录（2026-10-12，设备短暂在线）

脚本：`probe_caps.py`（逐条打命令）、`enum_hid.py`（枚举 VID/PID）、`list_udisk.py`（只读列 U 盘）

### 7.1 正常 HID 模式

| 项 | 结果 |
| --- | --- |
| INFO | ✓ `00 55 1a 00 00 xx xx xx xx xx xx xx xx 07 8c 14 0f xx xx xx xx 0f c8 33 32 fc 35`<br>SN = `xx xx xx xx`、固件版本 = `0xC8`(V2.00)、START 参数 = `33 32` |
| START | ✓ 参数对上后 2 秒收 335 帧（≈167 Hz） |
| **CMD 4** | 💀 有响应 `55 0B 04 "accept"` + 身份块 —— **但它同时把设备打进了 IAP**（见下） |
| CMD 1 / 2 / 5、55 帧、A5 帧 | ⏸ 未测成，设备随后被 CMD4 打进 IAP 模式 |

#### 💀 CMD 4 事故复盘（2026-10-12 08:00 定性）

**表象骗人**：它回的是 `accept` + 身份块，看着人畜无害（响应帧 `[2]` = CMD 回显，来自 `0x0804A74E`）。
**真相**（反汇编 `0x0804AACE` 分支）：

```
0804AAEA  movw r7,#0x7800 / movt r7,#0x800      ; r7 = 0x08007800
0804AAFA  ldrd r6,fp,[r7,#4]                    ; 先读出旧值
0804AB18  bl 0x802EEE0                          ; FLASH_Unlock()  （KEYR: 0x45670123 / 0xCDEF89AB）
0804AB1C  bl 0x802EA84    (r0=0x08007800)       ; FLASH_EraseSector()（CR bit1 SER + bit6 STRT）
0804AB26  bl 0x802EF04    (r0=0x08007800,r1=0xA); FLASH_ProgramWord(0x08007800, 0x0000000A)
0804AB2E/36/3E/46  再写 0x7804/08/0C/10 = 擦除前读出的旧值
0804AB4A  bl 0x802E9C8                          ; FLASH_Lock()
```

函数的身份靠寄存器写序列认死：`0x802EEE0` 向 `0x40022004`(FLASH_KEYR) 写标准解锁双字；
`0x802EA84` 置 `0x40022010`(FLASH_CR) 的 bit1(SER)+bit6(STRT) 并写 `0x40022014`(AR)；
`0x802EF04` 置 bit0(PG) 后 `str r1,[r0]`。寄存器基址 `0x40022000` → STM32F1 系（或 GD32/CH32 兼容）。

**后果**：`0x08007800` 那一页（2 KB）**在固件里是代码**，不是参数区 ——
`.tmp-fw2/RKX3.bin` offset 0x7800 处 0xFF 只占 2%（49/2048），前 64 B 是标准 Thumb
（`movw r0,#0x4000 / movt r0,#0x4001 / mov.w r1,#0x20000`…）。
擦除按**整页**走，写回只有 20 B → 余下 2028 B 变 0xFF → 应用跑飞/HardFault → **跳 IAP**。
IAP 升级器与 `0:/RKX3.bin`、`FlashIAP.bin` 等字符串在 bin offset `0x81E**` → `0x08081E**`，
**属另一个 bank**，所以 IAP 自己完好，照常挂 MSC 双盘、屏幕照常显示 `HID IAP`。

**三条教训**：
1. 不再实测"命令表里官方从没用过"的命令 —— 官方不用，多半因为它危险
2. 危险命令实测前，先把固件实现读完，确认无 Erase / Program / Reset 调用
3. "回什么"不能作为安全性判据 —— 必须核对**写操作**

**恢复**：官方固件 = `.tmp-fw2/RKX3.bin`（552,720 B，由 `RKX3V2.00.rar` 解出），
拷进 IAP 盘 `E:` 刷回（E: 当前是空的，只有一个读不出来的 `Ready.TXT`）。

### 7.2 ★ IAP 模式其实是 U 盘（MSC），不是 HID

⚠⚠ **不是用户按键进的 —— 是本轮 CMD4 把设备打进去的**（用户 2026-10-12 08:00 亲自纠正）。
设备此前从未进过 IAP：E 盘（RKX3IAP）的 `System Volume Information\IndexerVolumeGuid` 首次索引时间
= **2026-10-12 07:46:32**，与 CMD4 那轮实测同一分钟（F 盘同一文件是 2026-03-07）。
屏幕显示 `HID IAP`，实测：

| 模式 | VID:PID | 设备类 | 序列号 |
| --- | --- | --- | --- |
| 正常 | `2E3C : AF03` | HID | `XXXXXXXXXXXX` |
| IAP | `2409 : 0926` | **USB 大容量存储** | `XXXXXXXXXXXX` |

挂出两个盘：**E: RKX3IAP**（FAT 8.3 MB）+ **F: RKX3**（FAT 3.3 MB）。

→ 固件里那句 `HID IAP` 只是**界面文案**，真实升级通道是 **U 盘拷 bin**，
不是"通过 HID 传固件"。这跟官方说明书"按住返回键插线 → 拷 bin 进 RKX3IAP"完全对上。
→ 顺带回答了旧报告 §8 的待验证项：**`Ready.TXT` 就在 E: 盘根上**。

### 8.1 能读到（设备→主机）

| 数据 | 来源 | 状态 |
| --- | --- | --- |

## 9. 能不能读到"屏幕显示的信息"（协议类型、纹波）

分两层说：

**① 屏幕像素 / 截图 —— 读不到。**
没有"读屏"命令（命令表已枚举完），也没有任何能带长度参数的分块发送出口。
屏幕帧缓冲在 MCU 侧，HID 摸不到。

**② 屏幕上的那些"数值"—— 分两种：**

| 屏幕内容 | 能不能从 HID 等价拿到 | 怎么拿 |
| --- | --- | --- |
| 协议类型（PD3.0 / QC / UFCS …） | ✅ 能，而且比屏幕更细 | 解 0x30 事件帧里的 `Source_Capabilities` PDO；诱骗/Request 也能从 RDO 看 |
| 纹波 VPP / AVG | ❌ 拿不到（设备侧硬件检波，HID 无此字段） | 只能看屏幕 |

⚠ 有一个**待验证的口子**：0x1B 测量帧里还有两个未识别的 u16
（`[33..34]` 带载≈300、空载=0；`[61..62]` 带载=23、空载=0）。
纹波有没有可能就在其中一个，需要**带载时把屏幕读数和这两个字段对比**才能定。
设备退出 IAP 模式后可以这样验：接充电器带载 → 跑 `probe_caps.py` 抓几帧 →
把 `[33..34]` / `[61..62]` 的十进制值和屏幕上 VBUS Ripple 的 mV 数对一下。
