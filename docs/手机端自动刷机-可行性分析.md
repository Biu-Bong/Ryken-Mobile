## 0. 结论速览

| 问题 | 答案 | 依据 |
| --- | --- | --- |
| 固件里有「用命令进 IAP」的功能吗？ | ❌ **没有**。进 IAP 只认**硬件按键** | 反汇编 `0x080317A4` / `0x08031840`，见 §1 |
| 那 10-12 那次为什么进了 IAP？ | CMD4 把按键扫描代码擦了 2 KB → 设备异常落进 IAP | 见 §1.2 |
| 手机端能自动完成「进 IAP」吗？ | ❌ **不能**。必须物理按住「返回」键 + 重新上电，手机没有 GPIO 控制权 | §2 |
| 进了 IAP 之后，手机能自动刷机吗？ | ✅ **可行**，但要自己实现 USB MSC 客户端 + FAT32 写入（约 1000 行 Kotlin） | §3.2 |
| 有没有省事的路？ | ✅ 有：手机 ROM 若能挂载该 U 盘，App 只需写文件（但不通用） | §3.1 |

**一句话**：刷机链路能自动化**后半段**（写入固件），但**前半段（进 IAP）必须靠人手按键** —— 除非愿意让手机端复刻 CMD4 那种"打坏设备"的手段，那是产品自杀。

## 1. 「用命令进 IAP」的真相

### 1.1 命令表里根本没有这条路

HID 主机→设备只有三类帧，全部反汇编过（详见 `HID接口能力-取证报告.md`）：

- **AA 帧** 7 条命令（CMD0..6 + 0xFF START）
- **55 帧**：`memcpy(0x20005C08, buf+2, 48)` —— 纯 RAM
- **A5 帧** sub1/sub2/sub3 —— 纯 RAM

**没有任何一条通往 USB 重新枚举 / MSC / IAP 逻辑。**

### 1.2 进 IAP 的真实条件：GPIOB 第 2 位

唯一入口在 `0x08031750` 这个函数里：

```
08031782  ldrb.w   r1, [r8]            ; r8 = 0x2000505C 状态字节
0803178A  ldr      r0, [r7, #0x2c]     ; r7 = 0x20005398
0803178C  movw     sb, #0xc00
08031790  cmp      r1, #0xb
0803178C  movt     sb, #0x4001         ; ★ sb = 0x40010C00 = GPIOB
080317A4  mov      r0, sb
080317A6  movs     r1, #4
080317A8  bl       0x802FEE0           ; ★ 位测试：(GPIOB->IDR & 0x4) == 0x4 ? 1 : 0
080317AC  cbnz     r0, #0x80317c2      ; 为 0（键没按）→ 直接返回，啥也不干
   ...
0803183E  cbz      r0, #0x8031846      ; 复测一次
08031840  bl       0x8026B14           ; ★ 启动 USB MSC = 进入 IAP 模式
08031844  b        #0x803184a
08031846  bl       0x8026AE4           ; 否则走清零
```

`0x08026B14` 做的事：配置 USB 时钟/GPIO 与描述符表（`0x20000184` / `0x200001AC`，`0x40005C00` USB 外设寄存器），
末尾 `strb r5(=1), [0x20004714+5]` 置 MSC 会话激活标志。
`0x08006F68` 是配套界面函数：`adr r1,#0xd4` → `"0:main/iap.bmp"` + `adr r1,#0x98` → `"HID IAP"`，
由 UI 状态机在 `state == 0x1D` 时调用。

**结论：`GPIOB bit2` 就是「返回」键。按住它（配合上电时序）→ 进 IAP。纯硬件条件。**

### 1.3 那 10-12 那次到底发生了什么

CMD4（`0x0804AACE`）= `FLASH_Unlock` + `FLASH_EraseSector(0x08007800)` + 只写回 5 个字。

被擦的 2 KB 页（`0x08007800-0x08007FFF`）里装的是 **GPIOB Pin8/Pin9 的按键轮询 + 长按计数**
（反汇编 `0x08007800`：配 GPIOB → 循环 `bl 0x802FEE0(GPIOB, 0x200)` 读 Pin9 → 计数到 `0xFB`(251)×5 ms ≈
**1.25 s** 才返回 1）。

代码被抹成 `0xFF` 后，设备在后续某个循环里跑到那片区域 → 取指 `0xFFFFFFFF` → 异常 →
**落进 IAP**（厂商把 fault 兜到 IAP 防砖，是常见做法）。

> ⚠ 这是**故障态**，不是功能。任何"用命令把设备打进 IAP"的方案都等于"先弄坏它"，绝不能用于产品。

## 2. 为什么手机端无法自动「进 IAP」

| 环节 | 官方要求 | 手机能否代劳 |
| --- | --- | --- |
| 按住「返回」键 | 是（GPIOB bit2 被拉低/拉高） | ❌ 需要物理按键，手机只能通过 USB 发数据 |
| 重新上电 | 是（上电时序参与判定，见 `0x08031806` 段） | ⚠ 可以：插线即为上电，但必须与按键同时发生 |
| 触发重新枚举 | 按键状态下走 `0x08026B14` | ❌ 无任何 HID 命令可达此路径 |

**可行的最接近方案**：**用户手动按住「返回」键 → 把线插进手机**（而不是插进电脑）。
按键这一步永远得人来做，但"必须找台电脑"这一步可以省略。

## 3. 进 IAP 之后：手机端刷机的两条路

设备一旦进了 IAP，就是一个标准的 **USB 大容量存储设备**：
`VID 2409 / PID 0926`，序列号 `XXXXXXXXXXXX`，挂两个 FAT 卷（`RKX3IAP` + `RKX3`）。
刷机 = 往 `RKX3IAP` 卷根目录写一个 `RKX3.bin`，等文件名 `Ready.TXT` → `Success.TXT`。

### 3.1 路径 A：依赖手机 ROM 挂载 U 盘（简单，不通用）

**原理**：部分 OEM ROM 的 `vold` 支持挂载 USB MSC 卷；挂载后 App 走 SAF 或
`MANAGE_EXTERNAL_STORAGE` 写文件即可，**不需要碰 USB 协议栈**。

- ✅ 实现量小（就是"选目录 + 写文件 + 轮询文件名"）
- ❌ **不通用**：AOSP/Pixel 对 U 盘挂载支持残缺，各家 ROM 行为不一致
- ❌ 挂载点、权限模型差异大，还要处理"设备插上但系统不挂载"的降级路径
- ⚠ 需要在目标机型上实测：插上 IAP 设备后，系统"存储"里到底出不出现这个 U 盘

### 3.2 路径 B：App 自己实现 USB MSC 客户端（复杂，通用）

**背景**：Android 的 USB Host API **不提供大容量存储类驱动**，只给你 bulk 端点做裸传输。
所以要走这条路，得自己把 MSC 协议栈写完：

| 模块 | 内容 | 预估 |
| --- | --- | --- |
| USB 层 | `UsbManager` 打开设备、认接口（class 0x08）、claim bulk in/out 端点 | 复用现有 `RykenUsb.kt` 骨架 |
| MSC 传输层 | **Bulk-Only Transport (BOT)**：CBW(31B) 下发 / CSW(13B) 回收 / 复位恢复 | ~150 行 |
| SCSI 层 | `INQUIRY` / `READ CAPACITY(10)` / `READ(10)` / `WRITE(10)` / `REQUEST SENSE` | ~150 行 |
| FAT32 层 | 读 BPB / 遍历根目录（含 LFN） / 分配簇 / 写 552,720 B / 更新 FAT 与目录项 | ~600 行 |
| 状态机 | `Ready.TXT` → 写入 → 等 `Success.TXT` → 超时/断线处理 | ~100 行 |

**总计约 1000 行 Kotlin，纯 App 侧，零 ROM 依赖。**

**已知风险：**
1. **FAT32 写坏 = 升级盘变砖**（现在这块盘是设备唯一的救命通道，写错就没有第二次机会）
2. 写入过程中断线 → 设备停在 IAP 且固件不完整（不过 IAP 本身还在，可以重试）
3. 552 KB 的写入走 BOT 是 **8,632 个 64 字节事务**（若用 512B 块 = 1,079 次 WRITE(10)），
   耗时估计几十秒 —— 必须给用户明确的进度与"别拔线"提示
4. 设备端 IAP 是**单线程、一次机会**：写完就该看到 `Success`，没有二次握手

### 3.3 不可行的一条：HID 直刷

曾考虑"用 55 帧把固件灌进去" —— **已被反汇编否掉**。55 帧有两个分支，**终点都是 RAM**：

- `LEN == 0x18` → `memcpy(0x20005C08, buf+2, 48)` + 三个 u16 → `0x20004BC8`
- `LEN != 0x18` → `memcpy(0x20005638 + LEN*62, buf+2, 62)`（`rsb r0,r0,r0,lsl#5` = LEN×31 → `lsl#1`；
  LEN 为 8 位 → 上限 ~15.9 KB）

看着像"分包灌数据"，但**落在 RAM 缓冲里，全程没有任何 Flash 写入**；而固件本体 552,720 B
也远超 15.9 KB 的窗口。**HID 通道不是固件传输通道。**

### 3.4 命令空间已穷尽 —— 不存在隐藏的「进 IAP」命令

```
0804A754  cmp  r0, #6
0804A756  bhi.w 0x804a920        ; CMD > 6 全走这里
0804A920  cmp  r0, #0xff
0804A922  bne.w 0x804ac3e        ; ★ 不是 0xFF 一律丢弃
```

CMD 7..255 里**只有 0xFF（START）被受理**，其余直接退出。加上 AA 0..6 逐条反汇编过、
55 帧与 A5 各 sub 也全部读过 —— **主机侧能表达的所有帧型都查完了，没有一条通往
USB 重新枚举 / MSC / IAP。**

## 2.5 手机侧实测（Redmi K20 Pro / MIUI，2026-10-12）

设备已插在手机上，用无线 adb 探测：

| 探测项 | 结果 | 含义 |
| --- | --- | --- |
| `/dev/bus/usb/001/002` | 存在，时间戳稳定 | 设备**已枚举**，非反复重连 |
| `/sys/bus/usb/devices/1-1` | 存在 | USB 核心层认到了 |
| `1-1:1.0/driver` → | **`usbfs`** | ★ 接口**交给用户空间** → **App 可用 `bulkTransfer()` 直接读写** |
| 端点 | `ep_01`(OUT) + `ep_81`(IN) | 标准 HID 端点对，与 Windows 侧一致 |
| `/dev/hidraw*` | 不存在 | 内核 usbhid 未接管（对 App 无影响，反而少一层权限） |
| `/sys/bus/scsi/devices/` | 只有 `1d84000.ufshc` | 当前**不是 MSC 模式** |
| `/proc/mounts` | 无外部 vfat | 同上 |
| `dumpsys usb` | **崩溃** `IllegalArgumentException @ ByteStream.<init>` | MIUI 描述符解析被呛到。**只影响 dump，不影响 App 访问**（待 App 侧最终验证） |
| `1-1/idVendor` 等 sysfs | 全部 `Permission denied` | Android 10+ SELinux，非 root 读不到 VID/PID |

**结论**：**手机侧 USB Host 通路是通的**（`usbfs` + 成对 bulk 端点齐备）。
"进了 IAP 之后由 App 写固件"在通道层面没有障碍 —— 剩下两个未知项必须让设备真正进一次 IAP 才能验：

1. Android 会不会自动挂载 MSC 卷（`usb-storage` + `vold`）
2. App 能否拿到该卷的写权限

而"进 IAP"这一步，只能**人手按住返回键**。

## 4. 建议的产品形态

```
① 用户在设备上按住「返回」键
② 把线插进手机（OTG，设备由手机供电上电）
③ App 检测到 VID 2409 / PID 0926
④ App 往 RKX3IAP 卷写入 RKX3.bin（路径 A 或 B）
⑤ 轮询卷内文件名：Ready.TXT → Success.TXT
⑥ 提示"升级完成，请拔出重插"
```

**用户操作 = 按一个键 + 插一次线。** 比"必须找台电脑"实用得多。

**优先建议**：先做**路径 A 的实测**（在目标机型上插一次 IAP 设备，看系统是否挂载）。
如果主流目标机型都能挂载，路径 A 足够，省掉 1000 行；挂不上再上路径 B。

**必须承认的边界**：
- 进 IAP **永远**需要人手按键，这一环无法自动化
- 手机 OTG 能否稳定给设备供电（说明书要求"插线上电"）**尚未实测**
